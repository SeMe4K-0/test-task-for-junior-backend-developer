# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и
применяется только при инициализации пустого data volume.

## Swagger

Swagger UI:

```text
http://localhost:8080/swagger/
```

OpenAPI JSON:

```text
http://localhost:8080/swagger/openapi.json
```

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

## Реализация периодичности

Есть несколько способа реализовать множественность задач:
* никаких измений в таблицах не делать. Вместо этого создавать несколько записей в цикле; 
* добавить поля в уже существующую таблицу;
* создать новую таблицу, в которой будут храниться только даты;
* комбинация вышеуказанных способов.

Рассмотрим каждый вариант отдельно.

#### Цикл

Этот вариант очевиден: схема данных не изменяется, изменяются только параметры запроса к API.

_Плюсы:_ минимальная инвазивность, простота реализации в коде, простота описания нерегулярной повторяемости (просто
несколько записей в таблице).

_Минусы:_ необходимость строить запрос к базе динамически[^1] либо несколько запросов, невозможность описания
бесконечной повторяемости,  ID задач перестают быть предсказуемыми, значительное увеличение объёма данных в базе,
сложность удаления задачи.

#### Добавление полей

В этом варианте добавляются как минимум два поля: одно отражает тип задачи (раз в несколько дней, на фиксированное
число и т. д.), второе же имеет контекстный смысл, в зависимости от значения первого. 

_Плюсы:_ малый объём добавляемых данных (в простейшем случае), легко реализовать задачи с регулярной повторяемостью,
возможность описания бесконечной повторяемости, предсказуемые ID задач.

_Минусы:_ семантика одного поля зависит от значения другого, проблематичная реализация нерегулярной повторяемости
(придётся либо использовать массив в качестве значения поля, либо как-то ещё помещать несколько значений в одно поле),
сильно усложняется запрос на получение всех задач на заданную дату (вместо простой выборки по одному полю придётся
писать сложное условие)[^2].

#### Добавление таблицы дат

В этом варианте базовая таблица не изменяется, но добавляется новая, ссылающаяся на неё, и содержащая только даты, на
которые запланированы задачи.

_Плюсы:_ одна и та же реализация для произвольной конечной повторяемости, предсказуемые ID задач, относительно простой
запрос на получение всех задач на заданную дату (через `JOIN` или подзапросы).

_Минусы:_ невозможно релизовать бесконечную повторяемость, значительный объём добавляемых данных (хотя и сильно
меньше, чем для случая с циклом), необходимость динамически конструировать запрос в коде.

#### Комбинация

Возможно несколько вариантов комбинации. Наиболее логичным представляется создание дополнительной таблицы, в которую
помещаются данные о периодичности (если задача истинно периодическая) и даты, на которые поставлена задача (если у
задачи нерегулярная повторяемость). Таблица при этом ссылается на основную таблицу, где хранятся метаданные задач.

_Плюсы:_ возможность реализовать произвольную повторяемость, предсказуемые ID задач, баланс между объёмом данных и
возможностями представления задач.

_Минусы:_ требуется сложная логика при построении запроса на добавление, необходимость динамически конструировать
запрос, зависимость семантики поля от значения другого поля, сложные условия в запросах на получение задач по дате,
множество пустых либо игнорируемых полей.

[^1]: В случае, если бы проект был написан на Python и использовал, например, SQLAlchemy это не было бы проблемой для
программиста, однако в данном проекте запросы организованы в виде обычных строк, динамическое построение которых
вручную повышает вероятность ошибок.

[^2]: Такого запроса в данном тестовом проекте нигде не делается, однако в реальном проекте с большой вероятностью
он будет.

### Практические соображения

Требуется найти баланс между пользовательским требованиями, простотой реализации и поддержки кода, а также
работы с базой данных.

С точки зрения пользователя нет принципиальной разницы, как именно создана задача: одним запросом на создание
периодической задачи либо же множеством ручных запросов. Разница есть только при создании задачи, однако пользователь
при этом взаимодействует только с API (вероятнее всего, косвенно, через некоторый интерфейс), но не с базой напрямую.
Следовательно, пользователю не важно, как устроена база, важны лишь получаемые из неё данные. Кроме того, с практической
точки зрения маловероятно, что кому-то может потребоваться истинно _бесконечная_ повторяемость задач (хотя наличие такой
возможности может быть полезным). Для упрощения разработки и ускорения доставки новых возможностей пользователям можно
обойтись созданием периодических задач в определённом диапазоне (напр., «каждое седьмое число в течение следующих трёх
лет»). Минус — необходимость рефакторинга в случае, если реализовать истинно бесконечную повторяемость всё же
потребуется.

Желательно, чтобы запросов к базе было как можно меньше и чтобы они были как можно проще. По этой причине вариант с
циклом не подходит — огромное количество запросов при создании задачи и сложность при удалении задачи (придётся
каким-то образом выяснять, какие записи фактически относятся к одной задаче либо помечать связанные записи, что ещё
больше увеличит объём данных в базе).

Желательно, чтобы код был как можно проще. С этой точки зрения оптимальным был бы вариант с циклом, однако он не
подходит из-за большой нагрузки на базу. Второй по простоте вариант — дополнение таблицы полями, но он неудобен с
точки зрения реализации нерегулярной повторяемости. Наиболее сбалансированным при этом выглядит вариант с отдельной
таблицей, хранящей либо записи с датами для однократных и нерегулярных задач, либо тип периодичности и
контекстно-зависимое поле. Например, так:

| id | task_id | type | date       | frequency |
|----|---------|------|------------|-----------|
| 1  | 1       | 'O'  | 2028-04-03 | NULL      |
| 2  | 2       | 'S'  | 2028-04-02 | NULL      |
| 3  | 2       | 'S'  | 2028-05-07 | NULL      |
| 4  | 3       | 'M'  | NULL       | 5         |
| 5  | 4       | 'P'  | NULL       | 0         |

(Либо можно поле `type` перенести в основную таблицу.)

В таком варианте получение списка всех задач не меняется. Получение задач по дате (в простейшем виде) выглядит
громоздко, но не слишком сложно:

```sql
SELECT
    <desired_fields>
FROM tasks JOIN task_dates ON tasks.id = task_dates.task_id
WHERE 
    ((tasks.type = 'O' OR tasks.type = 'S') AND task_dates.date = '<desired_date>')
    OR (tasks.type = 'D' AND datediff('<desired_date>', task_dates.date) % task_dates.frequency = 0)
    OR (tasks.type = 'M' AND day('<desired_date>') = task_dates.frequency)
    OR (tasks.type = 'P' AND day('<desired_date>') % 2 = task_dates.frequency);
```

Для реализации выбираем этот вариант.
