## Что я добавил: расписания

Основная идея — дать пользователю возможность один раз описать                                                                                                                                                                                                            
правило повторения, а дальше пусть система сама ставит задачи.

Сделал отдельный ресурс `schedules`: по нему есть обычный CRUD.                                                                                                                                                                                                           
Пользователь создаёт расписание с заголовком, описанием и правилом                                                                                                                                                                                                        
периодичности, а в таблице `tasks` потом появляется новое поле                                                                                                                                                                                                            
`schedule_id` — если задача родилась из расписания, у неё там стоит                                                                                                                                                                                                       
ID шаблона. Для задач, созданных вручную, поле пустое.

### Какие типы периодичности поддерживаются

- `daily` — каждый N-й день, в параметрах `{"interval": N}`
- `monthly` — конкретное число месяца от 1 до 30, в параметрах `{"day": N}`
- `even` / `odd` — по чётным или нечётным числам месяца
- `custom_dates` — произвольный список дат в параметрах                                                                                                                                                                                                                   
  `{"dates": ["2026-04-15", ...]}`
- `end_of_month` — последний день месяца

### Про `end_of_month`

В ТЗ для ежемесячных задач диапазон заявлен 1–30. Но тут есть тонкость:                                                                                                                                                                                                   
в июле последний день — 31-е, в феврале — 28-е или 29-е. Если кому-то
нужно делать задачу именно в конце месяца, обычным `monthly` этого                                                                                                                                                                                                        
не закрыть. Поэтому я добавил отдельный тип — он сам вычисляет                                                                                                                                                                                                            
последний день текущего месяца, в том числе корректно обрабатывает                                                                                                                                                                                                        
високосные года.
В UI, думаю, можно добавить отдельную кнопку или подпункт в custom_dates, но
как именно будет лучше никто не знает - нужно тестировать.

### Как задачи появляются в трекере

Для создания задач по расписанию запустил отдельного воркера —                                                                                                                                                                                                            
он работает в фоновой горутине рядом с HTTP-сервером. Раз в
`SCHEDULER_INTERVAL` (по умолчанию час, в docker-compose стоит 30                                                                                                                                                                                                         
секунд чтобы было удобно посмотреть как оно работает) воркер:

1. берёт все активные расписания из БД
2. пропускает те, по которым уже создал задачу сегодня
3. проверяет, подходит ли сегодняшний день под правило конкретного расписания
4. если подходит — создаёт задачу в таблице `tasks` и помечает
   в расписании дату последнего создания

Защита от дублей сделана через поле `last_created_date` у расписания.                                                                                                                                                                                                     
Если сервис упадёт и перезапустится в течение того же дня, воркер                                                                                                                                                                                                         
просто увидит, что сегодня задача уже была создана, и ничего делать                                                                                                                                                                                                       
не будет.

### Допущения и ограничения

- Для `monthly` с `day=30` в феврале задача создаваться не будет —                                                                                                                                                                                                        
  30-го февраля не существует. Это осознанное решение: если нужен
  именно последний день месяца, есть отдельный тип `end_of_month`,                                                                                                                                                                                                        
  и смешивать эти сценарии мне показалось неправильным.
- В `custom_dates` даты валидируются при создании расписания через                                                                                                                                                                                                        
  `time.Parse` — Go сам отбрасывает несуществующие даты вроде                                                                                                                                                                                                             
  `2025-02-29` (невисокосный год), так что отдельную проверку писать                                                                                                                                                                                                      
  не пришлось.
- `last_created_date` — внутреннее поле воркера, через API его                                                                                                                                                                                                            
  выставить нельзя. Иначе пользователь мог бы случайно заблокировать                                                                                                                                                                                                      
  создание задачи на сегодня.
- При удалении расписания уже созданные по нему задачи остаются.                                                                                                                                                                                                          
  В БД это сделано через `ON DELETE SET NULL` — у задач просто                                                                                                                                                                                                            
  обнуляется `schedule_id`, сами они никуда не деваются. Мне                                                                                                                                                                                                              
  показалось это логичнее, чем каскадное удаление: врач мог уже
  частично выполнить задачи, не хочется у него их отбирать.
- `IsActive` при создании всегда `true`. Отключить расписание можно                                                                                                                                                                                                       
  обычным `PUT`, поставив `is_active: false` — воркер сразу                                                                                                                                                                                                               
  перестанет создавать по нему задачи.

### Новые эндпоинты

- `POST /api/v1/schedules` — создать расписание
- `GET /api/v1/schedules` — список всех расписаний
- `GET /api/v1/schedules/{id}` — одно расписание
- `PUT /api/v1/schedules/{id}` — обновить (в том числе активировать/отключить)
- `DELETE /api/v1/schedules/{id}` — удалить

### Пара слов про стиль кода

Старался писать новый код по примеру того, что уже было в проекте:                                                                                                                                                                                                        
те же слои (domain → usecase → repository → transport), те же                                                                                                                                                                                                             
паттерны с DTO и валидацией в сервисе, такая же структура ошибок                                                                                                                                                                                                          
и обработчиков. Были места, где хотелось переделать "под себя" —                                                                                                                                                                                                          
добавить логирование через middleware, вынести общие куски,                                                                                                                                                                                                               
иначе организовать обработку ошибок — но задача стояла именно                                                                                                                                                                                                             
добавить фичу, а не переписывать существующий код, поэтому                                                                                                                                                                                                                
я старался вписаться в уже заложенную архитектуру, а не ломать её.

# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## Swagger

Swagger UI:

```text
http://localhost:8080/swagger/
```

OpenAPI JSON:

```text
http://localhost:8080/swagger/openapi.json
```

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`
