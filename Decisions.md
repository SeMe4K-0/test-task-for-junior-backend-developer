# Комментарии по решениям

В этом файле описаны решения при реализации фичи периодичных задач

---

## Модель данных

### Таблица `task_generation_rules`, своего рода шаблон задач

Правила периодичности хранятся отдельно от задач. Задача привязывается к правилу через `rule_id`. Такую реализацию я выбрал чтобы можно было масштабировать в отдельную фичу, удалять уже создавать шаблоны для периодичных задач, отключать их, редактировать и так далее

### Поле `scheduled_for` в таблице `tasks`

Добавлено поле `scheduled_for` - дата, на которую задача была сгенерирована. Это нужно для того чтобы мы могли генерировать задачи сразу на неделю или месяц. Вместе с `rule_id` образует уникальный индекс чтобы избежать дублирования задач, которые уже были созданы, благодаря этому не приходится выполнять проверку в Go коде делая лишний запрос

```sql
CREATE UNIQUE INDEX unique_rule_scheduled_for
ON tasks (rule_id, scheduled_for)
WHERE rule_id IS NOT NULL AND scheduled_for IS NOT NULL;
```

**Реализация:** генерация задач (`POST /api/v1/tasks/generate`) идемпотентна - повторный вызов за тот же диапазон дат не создаст дубликаты. Это достигается через `ON CONFLICT DO NOTHING` в репозитории, без необходимости проверять дубликаты в Go-коде.

### Поле `due_date`

Оно не целенаправленно не используется в повторяющихся задач, но используется в одноразовых. Это срок выполнения.

## Типы периодичности

Реализованы четыре типа, не стал добавлять новые виды и делать их комбинированнми или обычными. При создании правила должен быть указан **ровно один** тип - это валидируется в usecase. Одновременное использование нескольких типов отклоняется с ошибкой `400 Bad Request`.

| Тип | Поле | Описание |
|---|---|---|
| Интервальный | `interval_days` | Каждые N дней, считая от `start_date` |
| По числам месяца | `month_days` | Массив чисел от 1 до 30 |
| По конкретным датам | `specific_dates` | Массив конкретных дат |
| Чётные/нечётные | `even_odd` | Значения: `"even"` или `"odd"` |

### Числа месяца ограничены 1–30

Задание говорит "от 1 до 30". Если же пользователю нужно создавать задачи на последнее число месяца, это нужно реализовывать отдельный вид периодичной задачи которая будет учитывать февраль и 31-ые числа.

## Поле `start_date` и `end_date`

Нужны чтобы задавать диапозон, оба поля необязательные, но если клиент не передает `start_date` будет задано сегодняшнее число

## Генерация задач

### `POST /api/v1/tasks/generate?from=YYYY-MM-DD&to=YYYY-MM-DD`

Максимальный диапозон для генерации задач ограничен 30 днями

Генерация задач вынесена в отдельный endpoint, а не происходит автоматически. 

Можно добавить воркер/крон которые будут запускать генерацию на заданный диапозон. Например воркер который будет запускать его стабильно каждую ночь

### Активность правил

Правило имеет поле `active`. Неактивные правила пропускаются при генерации. Деактивация используется вместо удаления, чтобы можно было в дальнейшем как удалить, так и отредактировать например продлив `end_date`

Автоматическая деактивация не реализовано, думаю это нужно реализовывать в воркере

---

## Worker: генерация задач

Воркер вызывает `CreateRecurrencedTasks` передавая туда текущую дату и `Interval` как часто он должен выполняться. По дефолту стоит раз в `60` секунд чтобы вы могли проверить работоспособность. В продакшне же я бы предложил запускать его каждый день ночью. 

## API: создание правила vs создание задачи

Используется один endpoint `POST /api/v1/tasks`. Наличие поля `recurrence` в теле запроса определяет тип операции:

- `recurrence` присутствует → создаётся правило периодичности, возвращается `recurrenceDTO`
- `recurrence` отсутствует → создаётся разовая задача, возвращается `taskDTO`

Такой подход я выбрал для текущего ТЗ, чтобы на клиенте не нужно было определять какой эндпоинт выбрать, но при необходимости можно вынести в отдельный эндпоинт. Разделить на клиенте на повторяющиеся задачи и одноразовые

## Что не реализовано (намеренно, из-за ограничений по времени)

- **Генерация по конкретному `rule_id`** - сейчас генерируются все активные правила. Но нужно добавить чтобы правила при создании новой `recurrence` вызывался метод который будет создавать задачи по `id` этого созданого `recurrence`
- **Изменение и удаление правил** - по сути обычный CRUD.
- **Пагинация и фильтры** в `GET /api/v1/tasks` и `GET /api/v1/recurrences` - планировал добавить получение задач за определенные дни, пагинацию, но не успеваю
