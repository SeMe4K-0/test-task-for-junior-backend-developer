# Task Service

Сервис для управления задачами с HTTP API на Go. Поддерживает создание одноразовых и периодических задач, пагинацию и мягкое удаление.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файлы из `migrations/` монтируются в `docker-entrypoint-initdb.d` и применяются только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

### Задачи (Tasks)

- `POST /api/v1/tasks` — создать задачу
- `GET /api/v1/tasks` — список задач (пагинация + фильтрация)
- `GET /api/v1/tasks/{id}` — получить задачу по ID
- `PUT /api/v1/tasks/{id}` — обновить задачу
- `DELETE /api/v1/tasks/{id}` — удалить задачу (мягкое удаление)
- `POST /api/v1/tasks/{id}/restore` — восстановить ранее удалённую задачу

#### Пагинация

Все списочные запросы задач поддерживают пагинацию:

```text
GET /api/v1/tasks?page=1&limit=20
```

| Параметр | По умолчанию | Максимум | Описание |
|---|---|---|---|
| `page` | 1 | — | Номер страницы (начиная с 1) |
| `limit` | 20 | 100 | Количество элементов на странице |

Ответ возвращается в обёртке с метаданными:

```json
{
  "items": [ ... ],
  "total": 150,
  "page": 1,
  "limit": 20
}
```

#### Фильтрация задач по дате

Параметры фильтрации комбинируются с пагинацией:

```text
GET /api/v1/tasks?scheduled_date_from=2026-05-01&scheduled_date_to=2026-05-31&page=1&limit=50
```

### Правила периодичности (Recurrence Rules)

- `POST /api/v1/recurrence-rules` — создать правило + сгенерировать задачи
- `GET /api/v1/recurrence-rules` — список правил
- `GET /api/v1/recurrence-rules/{id}` — получить правило по ID
- `PUT /api/v1/recurrence-rules/{id}` — обновить правило (пересоздаёт задачи)
- `DELETE /api/v1/recurrence-rules/{id}?delete_tasks=true|false` — удалить правило (мягкое удаление)

При удалении правила с параметром `delete_tasks=true` все сгенерированные задачи также мягко удаляются.


#### Мягкое удаление (Soft Delete)

При вызове `DELETE /api/v1/tasks/{id}` задача не удаляется из базы данных физически. Вместо этого проставляется поле `deleted_at`. Удалённые задачи не отображаются в списках и не доступны по ID.

#### Восстановление удалённой задачи

Если задача была удалена мягко, её можно восстановить:

```text
POST /api/v1/tasks/42/restore
```

После восстановления запись снова начинает возвращаться в `GET /api/v1/tasks` и `GET /api/v1/tasks/{id}`.


## Фича: периодические задачи

### Описание

Позволяет задавать правила повторения задач. При создании правила система автоматически генерирует конкретные задачи на каждую дату в указанном диапазоне.

### Типы периодичности

| Тип | Параметр | Описание |
|---|---|---|
| `daily` | `every_n_days` (по умолчанию 1) | Каждый N-й день |
| `monthly` | `day_of_month` (1–31) | Определённое число каждого месяца |
| `specific_dates` | `dates` (список дат) | Только на указанные даты |
| `even_odd` | `even_odd`: `"even"` или `"odd"` | Чётные или нечётные числа месяца |

#### Обоснование выбора типов

Данный набор типов периодичности был выбран для максимально полного покрытия рабочих сценариев медицинского персонала:
- **Daily (Ежедневные)**: Идеально подходит для рутинных процедур, таких как обход пациентов или ежедневные контрольные звонки. Возможность задать интервал (каждый N-й день) позволяет гибко настраивать задачи, повторяющиеся, например, раз в три дня, или раз в неделю.
- **Monthly (Ежемесячные)**: Необходимы для административных задач, таких как формирование ежемесячной отчетности или плановое обслуживание оборудования в конкретные числа месяца.
- **Specific Dates (Конкретные даты)**: Позволяет планировать уникальные, не имеющие строгого цикла события, такие как плановые операции или консилиумы, которые уже известны наперед.
- **Even/Odd (Чётные/Нечётные)**: Специфический, но важный сценарий для медицинских учреждений, где дежурства, инвентаризация или отчетность часто распределяются по чётности дней месяца для равномерной нагрузки.

### Примеры запросов

#### Ежедневная задача (каждый день в мае)

```json
POST /api/v1/recurrence-rules

{
  "task_title": "Обзвон пациентов",
  "task_description": "Ежедневный обзвон",
  "recurrence": {
    "type": "daily",
    "every_n_days": 1
  },
  "start_date": "2026-05-01",
  "end_date": "2026-05-31"
}
```

#### Ежемесячная задача (15-е число)

```json
POST /api/v1/recurrence-rules

{
  "task_title": "Формирование отчетности",
  "task_description": "",
  "recurrence": {
    "type": "monthly",
    "day_of_month": 15
  },
  "start_date": "2026-01-01",
  "end_date": "2026-12-31"
}
```

#### Задача на чётные дни

```json
POST /api/v1/recurrence-rules

{
  "task_title": "Инвентаризация",
  "task_description": "",
  "recurrence": {
    "type": "even_odd",
    "even_odd": "even"
  },
  "start_date": "2026-05-01",
  "end_date": "2026-05-31"
}
```

#### Задача на конкретные даты

```json
POST /api/v1/recurrence-rules

{
  "task_title": "Плановая операция",
  "task_description": "",
  "recurrence": {
    "type": "specific_dates",
    "dates": ["2026-05-10", "2026-05-20", "2026-06-05"]
  },
  "start_date": "2026-05-01",
  "end_date": "2026-06-30"
}
```

## Проектные решения и допущения

### Архитектура

- **Отдельная сущность `RecurrenceRule`**: правило повторения хранится как отдельная запись в БД. Оно содержит шаблон задачи (title, description) и параметры повторения. При создании правила система генерирует конкретные задачи (rows в таблице `tasks`) — по одной на каждую дату.
- **Немедленная генерация**: все задачи создаются сразу при создании правила. Это требует указания `start_date` и `end_date` (ограниченный диапазон), но исключает необходимость фонового процесса.
- **Транзакционность**: создание правила и генерация задач выполняются в одной транзакции PostgreSQL — либо всё создаётся, либо ничего.
- **Обратная связь**: каждая сгенерированная задача содержит `recurrence_rule_id` (FK) и `scheduled_date`, что позволяет отслеживать, из какого правила она создана и на какую дату запланирована.

### Пагинация

- Реализована через `page`/`limit` параметры с нормализацией значений (page >= 1, limit в диапазоне 1–100, по умолчанию 20).
- Ответ содержит `total` — общее количество записей, что позволяет фронтенду строить навигацию по страницам.
- Пагинация работает совместно с фильтрацией по дате: `total` учитывает только записи, подходящие под фильтр.

### Мягкое удаление (Soft Delete)

- Все операции `DELETE` выполняют мягкое удаление: вместо физического удаления записи проставляется поле `deleted_at`.
- Все `SELECT`-запросы автоматически исключают записи с `deleted_at IS NOT NULL`.
- Для задач реализован отдельный эндпоинт восстановления: `POST /tasks/{id}/restore`.
- При удалении правила периодичности с `delete_tasks=true` — связанные задачи тоже мягко удаляются.
- При обновлении правила периодичности старые задачи удаляются физически (hard delete), а новые создаются заново — это корректное поведение, т.к. при обновлении расписания старые задачи заменяются полностью.
- Частичные индексы `WHERE deleted_at IS NULL` обеспечивают, что мягкое удаление не замедляет запросы.

### Логирование запросов

Все входящие HTTP-запросы проходят через middleware, который логирует:
- Метод и путь запроса (`method`, `path`)
- Код ответа (`status`)
- Время обработки (`latency`)
- Адрес клиента (`remote_addr`)
- Query-параметры (если есть)

Уровень лога зависит от статус-кода: `INFO` для успешных ответов (2xx/3xx), `WARN` для клиентских ошибок (4xx), `ERROR` для серверных (5xx). Пример вывода:

```text
time=2026-05-01T10:00:00.000Z level=INFO msg="http request" method=POST path=/api/v1/tasks status=201 latency=12ms remote_addr=192.168.1.1:54321
time=2026-05-01T10:00:01.000Z level=WARN msg="http request" method=GET path=/api/v1/tasks/999 status=404 latency=1ms remote_addr=192.168.1.1:54321
```

### Граничные случаи

- **`day_of_month=31` в коротких месяцах**: день приводится к последнему числу месяца (например, 28 февраля, 30 апреля).
- **`specific_dates` вне диапазона**: даты за пределами `[start_date, end_date]` тихо отбрасываются.
- **`start_date > end_date`**: ошибка валидации.
- **Пустой результат**: если параметры не дают ни одной даты — ошибка валидации.
- **Защита от слишком больших диапазонов**: максимум 1000 задач на одно правило.
- **Удаление правила**: мягкое удаление с опциональным каскадным мягким удалением задач (`?delete_tasks=true`).
- **Обновление правила**: при обновлении правила старые сгенерированные задачи удаляются и создаются новые.
- **Високосный год**: для `monthly` с `day_of_month=29` февраль високосного года корректно обрабатывается (29 февраля).
- **Пагинация за пределами данных**: если запрошена страница больше последней, возвращается пустой массив `items` с корректным `total`.

### Что можно улучшить в продакшене

- **Фоновый планировщик**: вместо немедленной генерации — генерация задач «скользящим окном» (например, на 30 дней вперёд) с периодическим пересчётом.
- **Возможность привязки задачи к пользователю** (assignee) с авторизацией.
- **Миграции через инструмент** (golang-migrate) вместо init-скриптов Docker.
- **Просмотр удалённых записей**: фильтр `?include_deleted=true` для администраторов.
- **Курсорная пагинация** вместо offset-based для больших объёмов данных.
- **Rate limiting** для защиты от перегрузки.
